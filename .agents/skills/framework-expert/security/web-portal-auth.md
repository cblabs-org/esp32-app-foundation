# Web Portal Authentication

The Web Portal protects configuration endpoints and sensitive data using session-based authentication with SHA-256 password hashing.

## AuthManager

The `AuthManager` is a core framework service responsible for:
1. Validating credentials — passwords are hashed with SHA-256(salt ‖ password) using mbedTLS on hardware or a portable SHA-256 on native test builds.
2. Generating session tokens — 16 cryptographically random bytes from `esp_random()` (or `std::random_device` on native builds).
3. Validating incoming session cookies on API requests via `checkPortalAuth()`.
4. Validating MCP bearer tokens via `checkMcpAuth()`.

`AuthManager` implements `IWebContributor` (tab: "Security", order: 5, top-level bottom-nav) and `IConfigurable` (namespace: "auth", schema v1). Dependencies (`ConfigManager`, `KeyManager`) are injected via `begin()`.

## Auth Middleware

`PsychicHttp` supports middleware. The framework attaches a global authentication middleware in `WebServerManager` that intercepts requests based on path:

### Path Classification

| Path Pattern | Auth Required | Rationale |
|---|---|---|
| Non-API paths (HTML, CSS, JS, images) | No | Static assets must load before login |
| `/api/auth/status`, `/api/auth/login`, `/api/auth/password` | No | Must be accessible to perform authentication |
| `/api/tabs`, `/api/app` | No | SPA bootstrap data |
| `/api/system` (exact match) | No | System info; but `/api/system/restart` and `/api/system/factory-reset` REQUIRE auth |
| `/api/mcp/*` | Separate | MCPServer handles its own auth via `checkMcpAuth()` |
| All other `/api/*` paths | **Yes** | `checkPortalAuth()` enforced by middleware |

When a request arrives at a protected path:
1. The middleware calls `authMgr->checkPortalAuth(request, response)`.
2. `checkPortalAuth()` checks for a valid `esp32_session=<hex>` cookie.
3. If the session cookie matches the active session token (constant-time comparison via `_safeMemcmp()`), the request proceeds to the module's route handler.
4. If invalid or missing, a `401 Unauthorized` JSON response is returned. The module's route handler is never executed.

## Public Path Bypass

Certain routes must be accessible without a session cookie. The middleware maintains a bypass list:

- `/api/auth/login`: The endpoint where the client submits credentials to obtain the session cookie.
- `/api/auth/status`: Returns the current auth state (enabled, session active, password set, cert present).
- **Static Assets**: All requests that do not begin with `/api/` (such as requests for `.html`, `.css`, `.js`, and image files) pass straight to the static file handler.

The SPA client is responsible for intercepting `401` responses from the API, destroying the local session, and redirecting the user to the login screen.

## Token Lifecycle

### Session Token
- Generated by `_generateSessionToken()` as 16 bytes of `esp_random()` output.
- Delivered to the client as an `HttpOnly; SameSite=Strict` cookie: `esp32_session=<32 hex chars>`.
- Validated via `_checkSessionCookie()` which parses the `Cookie` header, decodes the hex value, and performs a constant-time comparison.
- A session is active when `_sessionToken` is not all-zero.
- Logging out clears `_sessionToken` to all-zero.

### Password Storage
- Passwords are hashed as `SHA-256(16-byte random salt ‖ password)`.
- The salt and hash are stored as hex strings in `KeyManager` under keys `"portal_password_salt"` and `"portal_password_hash"`.
- Verification uses `_verifyPassword()` which re-computes the hash and performs a constant-time comparison.

### MCP Bearer Token
- The MCP bearer token equals the stored password hash (deterministic, hex string).
- Retrieved via `GET /api/auth/mcp-token` (requires an active portal session).
- This avoids introducing a second credential — the same `KeyManager` entry is reused.

## Auth for MCP Server

`AuthManager` also protects MCP (Model Context Protocol) endpoints via `checkMcpAuth()`. The `MCPServer` module calls `_authManager->checkMcpAuth(request, response)` on every incoming HTTP-based MCP request:

- **When auth is disabled** (`_authEnabled = false`): returns `true` unconditionally — open access.
- **When auth is enabled**: validates the session cookie first (for browser-based MCP access), then falls back to checking the `Authorization: Bearer <token>` header. The bearer token must match the stored password hash (constant-time comparison).
- **Serial/USB transport**: MCP requests via serial `_processLine()` are intentionally NOT guarded — physical serial access is treated as trusted.

The `/api/mcp` path prefix is explicitly excluded from the global portal auth middleware to avoid double-checking — `MCPServer` handles its own authentication independently.

## AP Mode Bypass

When the device is in AP (Access Point) mode — typically during initial physical setup — `checkPortalAuth()` returns `true` unconditionally regardless of authentication state. This is controlled by `setAPMode(bool)`, called by `Application::begin()` after `AuthManager::begin()` with the `WifiManager` AP mode state.

## CORS Policy

The framework does not implement explicit CORS headers. The Web Portal is a same-origin SPA served from the device itself, so cross-origin requests are not expected. The `PsychicHttp` server does not set `Access-Control-Allow-Origin` or related headers. This means:
- Browser-based JavaScript from other origins cannot call the device's API.
- The MCP API is accessed via direct HTTP calls (e.g., from AI agents), not from browser cross-origin contexts.

## TLS for the Portal

`AuthManager` can generate an EC P-256 self-signed certificate via `generateAndStoreCert()`, stored as DER-encoded files at `/etc/server.key` and `/etc/server.crt`. When TLS is enabled (`isTlsEnabled()`) and a certificate is present (`hasCert()`), `WebServerManager` serves HTTPS on port 443 with automatic HTTP→HTTPS redirect on port 80. TLS is controlled independently from authentication via the `_tlsEnabled` flag, persisted under the `tlsEnabled` key in the auth config namespace. The `POST /api/auth/tls` endpoint allows toggling TLS on or off.

Certificate details:
- **Algorithm:** EC secp256r1 (P-256)
- **Subject CN:** `<hostname>.local`
- **Static buffers:** Certificate loaded into a 1024-byte static buffer, key into a 256-byte static buffer (avoids heap fragmentation).
- **Generation is async:** Uses an `std::atomic<bool>` concurrency guard (`_certGenRunning`) to prevent concurrent generation.

> **Note:** The `GET /api/auth/status` response now includes `tlsEnabled` in the JSON payload, reflecting the current state of the `_tlsEnabled` flag.

> **Cookie security:** The `Secure` flag on session cookies is conditioned on `isTlsEnabled() && hasCert()` (not `isAuthEnabled()`). This ensures the `Secure` attribute is only set when the connection is actually served over HTTPS.

## Operational Safety: Changing Credentials

Changing any device credential — the portal password, the WiFi network, or an
OTA/PAT bearer token — can lock an agent (or the user) out of the running
device. A device with an unknown portal password, or one that has silently
dropped off the network after a WiFi change, may only be recoverable by a
physical reflash. Before changing a credential, always:

1. **Establish an independent recovery path first, and verify it works.** The
   serial/USB MCP transport is the canonical fallback: it is intentionally
   unguarded by portal auth (physical access is trusted — see *Auth for MCP
   Server* above), so it keeps working even when the portal password is unknown
   or WiFi is down. Confirm serial MCP access *before* applying the change, not
   after discovering you are locked out.
2. **Tell the human the new credential and the recovery path before applying
   it** — never change a credential silently.

For WiFi specifically, prefer a change path that keeps the device reachable
(e.g. the AP-mode fallback) rather than committing a single new SSID that, if
wrong, strands the device on an unreachable network.
