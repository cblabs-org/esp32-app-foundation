## Implementation Checklist

### 1. Update `docs/design_specification.md` — §13.3

- [ ] Find the existing §13.3 (OTA pipeline section) and expand it with:
  - **SemVer Engine**: `FirmwareVersion` struct, packed 32-bit comparison, `parseVersionTag()` for git tags, channel-aware ordering (STABLE > RC > BETA > DEV)
  - **Release Channels**: Three channels (`stable`/`beta`/`dev`), channel stored in OTA IConfigurable config at `/mod/ota.json`, implicit downgrade when channel changes, `lastCheckedChannel` tracking
  - **Multi-Architecture Manifest**: `manifest.json` schema with per-board assets, `BOARD_ID` compile-time injection, `OTAManifest` parser, legacy fallback for pre-manifest releases
  - **Auto-Rollback**: `markAppValid()` called at Step 17b in Application boot sequence (after `_compactAndLock()`), self-test barrier covers all subsystem initialization, `CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE=y`
  - **Anti-Rollback**: NVS `security_version` counter, compared against compiled-in `SECURITY_VERSION` macro, prevents downgrade past security fixes
  - **Fail-Closed OTA**: When `otaPublicKey` is configured, missing or empty `.sig` file causes abort (not warning). Without a key, verification is skipped (dev convenience).
  - **Task Watchdog**: OTA FreeRTOS task subscribed to TWDT, fed during download chunks, `CONFIG_ESP_TASK_WDT_PANIC=y` — hung download → panic → reboot → auto-rollback
  - **Config Lifecycle**: Three-Tier model (Active/Previous/Golden) via `ConfigManifest`, snapshotted at blessing (Golden) and before OTA (Previous)
  - **CI/CD Pipeline**: GitHub Actions builds on tag push (matrix: esp32dev + esp32s3nano), local signing via `deploy_release.py`, `manifest.json` generated by `generate_manifest.py`
  - **Web Portal**: Channel dropdown (activated from PR-14 stubs), rollback with typed "ROLLBACK" confirmation, `setChannel` API, enhanced status endpoint

### 2. Create `docs/OTADeveloperGuide.md`

- [ ] **Overview**: Brief architecture summary with the component relationships:
  - `SemVer` → `OTAManifest` → `OTAUpdateManager` → `OTADownloadEngine` → `IOTAVerifier`
  - `ConfigManifest` ↔ `ConfigManager` ↔ `OTAUpdateManager`
  - `GithubClient` ↔ `OTAUpdateManager`

- [ ] **Release Workflow**: Step-by-step guide
  1. Code → commit → tag (`v3.1.0` or `v3.2.0-beta.1`)
  2. Push tag → GitHub Actions CI builds both architectures
  3. `gh run download <run-id>` → download unsigned artifacts
  4. `python3 scripts/deploy_release.py --tag v3.1.0 --run-id <id> --private-key private_key.pem`
  5. Script signs, generates manifest, creates GitHub Release with all assets

- [ ] **Key Management**:
  - Generate: `scripts/generate_keys.sh` → `private_key.pem` + `public_key.pem`
  - Embed public key: compile into firmware via `publicKey.hpp`
  - Storage: private key is local-only, NEVER committed to git
  - Rotation: physical re-flash required (no NVS override — prevents attack vector)
  - Compromise scenario: generate new key pair, flash all devices with new public key

- [ ] **Channel Testing**:
  - Subscribe a dev device to `beta` or `dev` channel via web portal or API
  - `POST /api/ota { "action": "setChannel", "channel": "beta" }`
  - Device will find pre-release tagged with `beta` in GitHub
  - Switch back to `stable` → implicit downgrade to latest stable release

- [ ] **Config Lifecycle — Three-Tier Model**:
  - **Active**: current running config per module
  - **Previous**: snapshot taken before each OTA download
  - **Golden**: snapshot taken when firmware is blessed
  - Managed by `ConfigManifest` at `/config_manifest.json`
  - Diagram showing: OTA download → snapshot Active→Previous → flash → reboot → self-test → bless → snapshot Active→Golden

- [ ] **Rollback Scenarios**:
  1. **Auto-rollback**: firmware crashes before `markAppValid()` (Step 17b) → bootloader reverts
  2. **Manual rollback**: web portal "Rollback" button (requires typing "ROLLBACK") or `POST /api/ota { "action": "rollback", "confirm": "ROLLBACK" }`
  3. **Channel downgrade**: switch from `beta` to `stable` → OTA applies latest stable even if version is "lower"
  4. **Anti-rollback**: `SECURITY_VERSION` prevents downgrade past security-critical firmware

- [ ] **Production Hardening** (from assessment findings):
  - Flash Encryption: how to enable for production builds (ESP-IDF menuconfig)
  - Secure Boot v2: hardware root of trust on ESP32-S3 
  - Impact: flash encryption makes NVS tamper-proof (security_version protected)
  - `setInsecure()` TLS trade-off: acceptable because mandatory signature verification is the security boundary, not TLS certificate pinning (GitHub CDN uses rotating certs)
  - Current build is explicitly "dev-grade" without flash encryption

- [ ] **Security Gap Register** (deferred to future PRs):
  - Full endpoint authentication for all state-changing web/MCP routes
  - POST body size enforcement (currently commented out in `WebServerManager`)
  - DataManager mutex hand-off restructuring

- [ ] **API Reference**:
  | Endpoint | Method | Body | Description |
  |----------|--------|------|-------------|
  | `/api/ota` | GET | — | Status check |
  | `/api/ota` | POST | `{ "action": "checkGithub" }` | Check + perform update |
  | `/api/ota` | POST | `{ "action": "status" }` | OTA state, version, channel, board |
  | `/api/ota` | POST | `{ "action": "setChannel", "channel": "beta" }` | Change update channel |
  | `/api/ota` | POST | `{ "action": "rollback", "confirm": "ROLLBACK" }` | Rollback firmware |
  | `/api/ota` | POST | `{ "action": "markValid" }` | Bless firmware |

- [ ] **Troubleshooting**:
  - "Update rejected — Missing .sig file": release has no signature file, and firmware has a public key configured. Add the `.sig` file to the release.
  - "No firmware for this board in manifest": the `manifest.json` doesn't have an entry for this device's `BOARD_ID`.
  - "Security version too low": firmware's `SECURITY_VERSION` is lower than the stored NVS value — this is anti-rollback protection.
  - Auto-rollback keeps reverting: new firmware crashes before Step 17b — check boot logs.
